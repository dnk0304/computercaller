1. THE FIRST ONE WAS MINE, AND WAS FIXED RATHER THAN EXCUSED.
   The two dirty paths were `.hb.pid` (my heartbeat's PID file) and
   `gate-run.log` — I had redirected the gate's stdout INTO the worktree I was
   asking it to certify as clean. Not a code defect, not base-inherent, and so
   not excusable. Both moved outside the worktree; run 2 reports dirtyPaths:0.

   Worth keeping as a rule: a step that grades the cleanliness of a tree can be
   failed by the act of recording the run. THE LOG BELONGS OUTSIDE THE SUBJECT.
   (I nearly repeated it: the first draft of this note was written into
   e2e-evidence/ while run 2 was live. e2e-evidence/*.txt is not in the gate's
   OWN_OUTPUT allowlist, so it would have been a dirty path. It landed seconds
   after the check had already run, and was parked outside the worktree until
   commit so the tree still matched exactly what the gate certified.)

2. THE OTHER THREE ARE ONE EVENT, AND IT IS BASE-INHERENT.
   ext-badge-counter-proof reported {"passed":32,"total":32,"attempts":2} — every
   check it made PASSED and then the process did not exit. exit=124 is a TIMEOUT,
   not an assertion. reap and baseline-parity are the same event counted twice
   more: a timed-out step cannot appear in harnessPass, and the survivor the reap
   census sees is the process that failed to exit.

   MEASURED AT BASE, NOT ASSERTED: P0.3's committed gate-P0.3-637b6f9.json, run
   on the commit that became this lane's base, shows
       FAIL harness:ext-badge-counter-proof exit=124
       FAIL reap:harness-batch              exit=1
       FAIL baseline-parity                 exit=1
   — the same step with the same exit code, while git-identity-clean-base-ancestry
   PASSED there. So the badge family predates this lane and the dirty-tree failure
   did not.

   Root cause is already named and owned: scripts/lib/reap.mjs censuses survivors
   immediately after taskkill /F with NO settle window, and each harness's
   `finally` rmSyncs a Chrome profile dir a live chrome still holds. P0.3
   diagnosed it; Ken relayed it to P5a-UI letter (f) as the R-AE family.

   WHY IT DID NOT REPRODUCE IN RUN 2: run 1 was contended — the P5B android gate
   was running on the same box from 04:00 and ~46 chrome processes were live. Run
   2 started after P5B finished. That is consistent with P0.3's diagnosis (a
   teardown race that loses under load), and it is the reason run 1 is kept: a
   green run on a quiet box is not evidence that the race is gone, and nobody
   should read 67/67 as retiring the R-AE ticket.
